# The core

One reader and writer of Cells, in Rust, that every surface uses: the command line, the page (as WebAssembly), the Mac (a C ABI in an XCFramework, under the Swift package in `swift/`), the language server (`cells lsp`, [EDITORS.md](../EDITORS.md)), and the daemon (`cells serve`, [ENGINE.md](../ENGINE.md)). [SPEC.md](../SPEC.md) is the law and [tests/](../tests) holds it to it.

| Crate | What it is | Depends on |
|---|---|---|
| `cells` | the reader, the writer, the columns, formulas, imports, the Arrow export, and `folder`: a folder's files, what each reads, and what a change reaches and stores, decided with no disk, clock or thread | nothing; `no_std` with `alloc`, the `std` feature adds threads |
| `cells-cli` | `cells check`, `fix`, `fmt` (and `--check`), `diff`, `merge`, `pin`, `run`, `allow`, `history`, `show`, `chart` (ratatui), `editors install` (the grammar and queries it carries), `skill` (the agent skill; it, `help` and the usage rendered from one description, `describe.rs`), `serve` (the daemon's), `lsp`, the language server (tower-lsp), and `sql`, which runs `cells-sql`; a file an editor holds open read as it holds it | `cells`, `cells-daemon`, `cells-disk`, `tokio`, `tower-lsp`, `ratatui`; `git` for `merge`, `hx` for `editors install helix`, `cc` for `editors install neovim` |
| `cells-sql` | `cells sql`: a folder asked as one database through DuckDB, a binary of its own ([below](#cells-sql)) | `cells`, `cells-disk`, `libduckdb-sys` (DuckDB 2.0.0 bundled) |
| `cells-disk` | files as a disk holds them, for `cells` and `cells-sql`: imports followed by path, through git for a `rev`, and from a cache of pinned URLs by their hash, else fetched; the `.cells` files a path names | `cells`; `git` and `curl` when a file asks |
| `cells-daemon` | the engine kept running over folders: `World`, its one way to the disk, the clock and change events (`Disk`, FSEvents through `notify`); `Daemon`, what was heard handed to the folder and what it decides written, only over the version it was made from; the folder's log (`.cells/log.jsonl`), its history, the schedules (`schedule`) and the trace (stderr, or the host's writer); the socket and its client (`wire`, `server`, `client`), and who may connect, by the kernel's word and the client's code signature (`trust`); a script run with Bun; and a static library with one C function, `cells_engine_serve`, for the app that hosts the engine (`build-apple.sh`: the library, arm64, and the `cells` and `cells-sql` commands the app signs, into `target/apple/engine`) | `cells`, `notify`, `jiff` (a schedule's zone), `serde`, `serde_json`, `tracing`, `libc` (local time, `getpeereid` and the audit token on a Mac, `SO_PEERCRED` on Linux), `core-foundation` and `security-framework-sys` (code signatures); `bun` when a script runs |
| `cells-wasm` | the core as WebAssembly, and `js/cells.ts`, a synchronous reader on it | `cells` without `std` |
| `cells-ffi` | the C ABI, `cells.h` (cbindgen), `CellsCore.xcframework` | `cells` |
| `cells-bench` | budgets generated and read, against the csv crate | `cells`, `csv` (bench only) |

`cargo test` runs the conformance suite (`Cells_SUITE`, else `../tests`), the properties (written back is the same bytes, an edit reads back as written, a tail read alone is the whole read, the parallel reading is the sequential one, columns reshaped keep their cells, a file written in another dialect reads back its cells, each for `.cells` files and for plain ones) and each module's own tests.

## `cells`

```rust
let mut doc = cells::read(bytes)?;          // or read_parallel(bytes, threads)
let doc = cells::read_with(bytes, &mut cells::files::Files::new(&held, "books/money.cells"), 1)?; // imports followed
doc.rows(); doc.columns(); doc.problems(); // problems by row, then column
doc.value(row, column);                    // Value::Decimal, ::Date, ::Choice, ...
doc.columns()[k].origin(row);              // Origin::Written, ::Formula (the column's), ::Cell (its own)
doc.tables(); doc.scripts(); doc.named();  // the prelude's tables, scripts and types, imported ones too
doc.describe(&doc.problems()[0]);          // row 3, cost: "8x.50" is not a number
doc.why(&doc.problems()[0]);               // "8x.50" is not a number
doc.set_cell(row, column, "90.00")?;       // or set_value, set_type ("EUR=cost * qty", written in shorthand)
doc.write();                               // every unchanged byte as read
let doc = doc.extend(grown_bytes)?;        // only the appended records read
let doc = doc.rearranged(&[Row::Kept(2), Row::New(&["fuel", "1"])], threads)?; // rows moved, added, out
let doc = doc.reshaped(&[ColumnAt::Kept(1), ColumnAt::Renamed(0, "item"), ColumnAt::New("note", &[])], threads)?;
let csv = cells::read_as(bytes, Dialect::Plain(cells::detect(&bytes)), threads)?; // a .csv, a .tsv
csv.written_as(Dialect::Cells, Some(&["item: text", "cost: EUR"]));          // another dialect
let spans = cells::tokens::tokens(text);    // what each part of any text is, a broken one too
doc.apply(&Change::Cell { row: RowAt::Key("INV-7".into()), column: "amount".into(), was: Some("950.00".into()), text: "1000".into() })?;
let doc = doc.assign_ids(|| random_bits())?;
let (schema, array) = cells::arrow::export(&doc);
```

- **Reading.** Records are found 64 bytes at a time: quote and separator bitmasks (NEON, SSE2, wasm SIMD, else a portable loop), quoted stretches by prefix XOR; a block that breaks RFC 4180 is read again byte by byte, which names the record. Field spans are batched 4096 rows at a time and decoded column by column, each kind of column in a loop of its own. A batch's bytes are searched for control characters first, 64 at a time (a table lookup on NEON, compares elsewhere, a block with a byte 0xC2 read exactly against the byte after it); in a batch holding one, a cell is broken when one starts inside its span, so no cell's text is read twice (1M rows: 1% on one thread with none, 5% with one every thousand rows). `read_parallel` splits the body at record boundaries (quote parity), reads the parts on threads, joins each column on its own thread and checks keys on threads; its result is `read`'s byte for byte. The core starts no thread unless asked.
- **Columns** are Arrow's layout: `i64`; `Decimal128(38, s)` at one scale per column (the most digits after the point any value has); `Date32`; `Time32[s]`; `Timestamp[s|ms|us|ns, UTC]` at one unit per column; bits; `i16` dictionary indices; `utf8` offsets and bytes; a validity bitmap each. Buffers are `Arc`-shared: an export hands them out, an edit copies only what someone still holds.
- **Problems** by place and kind (`type`, `missing`, `key`, `ragged`, `formula`, `reference`, `stale`), keys compared by value; a control character in a cell is a `type` problem (`Why::Control`, its code point), and `set_cell`, `set_value` and a new row's or column's cells refuse one (`Err` at the row, the doc untouched). **Errors** by place: `At::Header`, `Column(n)`, `PreludeLine(n)`, `Prelude`, `Row(n)`, `File`.
- **The prelude** (`prelude::parse`, `Statement`): types, imports, tables in `` ```cells `` fences, scripts with their schedules (`Schedule`, `Trigger`), read in order, fence-aware, so a `---` inside a fence closes nothing. A table in a fence is read as a file of its own with the types and tables above it.
- **Formulas** (`expr`): parsed, resolved against a `Scope` (every name a place, every kind checked before anything runs) and evaluated against a `Source`, lazily, each computed cell once, so formulas read each other in any order and a cell that reads itself is found. Exact decimals (`exact::Exact`): `+ - *` exact, `/` and `AVG` to 15 significant digits, half to even, its whole part kept (34 in a column with a scale, which rounds the result again). What a formula gives is written as text and read by its column's decoder, so a result is checked exactly as a typed cell is.
- **Imports** (`Imports`, `read_with`): a reader is handed what follows them. `files::Files` follows them through files a host holds by path (the suite, a page), checking a pin's SHA-256 (`sha256`); `Alone`, `read`'s, follows none, so what a file imports reads as unchecked. A doc read again after an edit takes its imports as they were followed.
- **Identity** (`RowAt`, `Change`, `Refused`, `Version`): a row by its key, its id, or its text; a change applies only to the cell it was made against. Ids come from bits the caller gives.
- **Rows rearranged** (`Doc::rearranged`): the file with exactly the rows asked, each kept one its record as it is now, each new one written from its cells, read again. Moving, adding and taking out rows; the reader is fast enough that it is the whole file read again (13.8 ms at 1M rows on 18 threads).
- **Columns reshaped** (`Doc::reshaped`, `ColumnAt`): the file with exactly the columns asked, each kept one its header cell and every row's field as written, a renamed one its type and formula kept, a new one its header cell and cells, read again. Inserting, removing, moving and renaming columns; a `.cells` file whose columns would no longer read (two of one name, a formula reading one taken out) is refused, the doc untouched.
- **Plain files** (`Dialect::Plain`, `detect`, `read_as`): a `.csv`, a `.tsv` or plain text, its separator (`,` `;` `\t` `|`) the one its first lines agree on, kept on write. The header is names alone, no prelude, and nothing is refused but bytes that are not UTF-8: a row of another width reads as blanks with a `ragged` problem (its fields past the header kept), a stray quote is text, a quote never closed runs to the end, a lone `\r` ends a line, and a blank or repeated name is a header problem (`Doc::naming`). An edited cell is quoted for the file's separator, and always in a file that quotes every field (`Doc::quotes_all`). The scanner takes the separator as a byte, so its speed is the comma's. tests/README.md, "Plain files", is the reading.
- **Another dialect** (`Doc::written_as`): a plain file written as Cells (with the header cells a conversion types it by, its text that would read as a formula escaped) or with another separator, a `.cells` file written plain (every computed cell its value); a record kept as written where nothing changes it.
- **Spans** (`tokens::tokens`): the text read as what each part is, the fences, comments, the prelude's statements (imports, a schedule's words, a script's code), every header cell's name, its type's parts (base, mark, bound, format, choice, reference) and its formula's, a table written inline as a table, and every cell by its column, a cell's formula by its parts. Read from the text alone, never refused, a part with no meaning an `Error` span. What Cells.app colours a `.cells` file by.
- **Places** (`Doc::place`, `header_span`, `cell_span`, `expr::names`): what is at a byte of the text, where each header cell and cell is, every name a formula reads with each part where it is written. What the language server finds, follows and renames by.
- **Breaks and spans** (`Doc::broken`, `Doc::spans`, `Doc::broken_spans`): where the grammar breaks, each break taking out only what it breaks, and where every problem and break is in the text written now.

A formula column costs its evaluation: 1M rows with `total: EUR = cost * qty` read in 236 ms on one thread and 170 ms on eighteen (the file without it in 74 and 12), the formula evaluated on one thread, its results written as text and read again by the column's decoder.

## `cells chart`

```console
$ cells chart <file> [n …] [--watch] [--svg] [--glyphs fine|blocks|ascii] [--colors true|256|16]
```

A file's charts ([SPEC.md, Charts](../SPEC.md#charts)), what each draws the engine's (`Doc::summary`), drawn here. No number lists them, `1  Spending by month  bars`, a file with none its one drawn from its columns as `0`; numbers draw those charts, one under another, at the terminal's width. `--watch` holds them on the alternate screen, all of them sharing it, drawn again when the file changes and when the terminal is resized; `q` or Esc leaves. `--svg` writes each as the engine's SVG instead, for a page or a README.

What the terminal holds is guessed and can be said: `TERM=linux` (the kernel's console: sixteen colours and a console font, no braille) draws in half blocks and eighths; `TERM=dumb` in ASCII; any other terminal in braille's dots, in true colour when `COLORTERM` says so, else 256 colours or sixteen. A tint is drawn in its dark theme's colour, quantized to the terminal's. Bars are eighth blocks along the value, two stacked series meeting in one cell drawn as its ink and its ground; lines, steps, areas and points are braille, or half blocks, or dots. On a Linux console of its own, kmscon (Fedora 45's console) draws braille and true colour where the kernel's console draws neither.

The drawing is ratatui's cells (`ratatui` 0.30 with its crossterm backend), in `cells` itself: no pixels, since a terminal's graphics (kitty's, sixel) would need an SVG rasterizer of a few megabytes in the binary every editor's language server is.

## `cells sql`

```console
$ cells sql <file|folder>... "<query>"
```

A folder asked as one database through DuckDB 2.0.0, in a binary of its own, `cells-sql` (`rust/cells-sql`), which `cells sql` runs, found beside the `cells` binary (the one a link on the PATH points to) or on the PATH; DuckDB built from its bundled sources (`libduckdb-sys`, pinned, its C API alone: the `duckdb` crate would add arrow-rs and some hundred crates for a Rust layer nothing here uses). Every `.cells` file under the paths is a table named by its stem, and so is every file they import from the disk (an import through git's history or a URL is read for the file importing it, never as a table) and every table a prelude writes, by its name. Tables of one name are one table: every `money.cells` under the folder is `money`, its columns joined by name in the order they first appear, null in a file without them. Every table has one more column, `file`, the path its row is read from, as `cells check` prints it; a file with a column of that name stops the query. The query is DuckDB's SQL, whole; its answer is written as `cells show` writes a table, tab-separated, a header of the columns' names, each cell its value, a null an empty cell. No extension is installed or loaded because a query names one (`autoinstall_known_extensions` and `autoload_known_extensions` off), so a query fetches nothing.

| Cells | DuckDB |
|---|---|
| `text`, `url`, `email`, `id` | `VARCHAR` |
| `int` | `BIGINT` |
| a currency | `DECIMAL(38, s)` at its scale: `EUR` 2, `EUR(6)` 6, `JPY` 0 |
| `num`, `pct` | `DECIMAL(38, s)`, `s` the most digits after the point a value of the table holds |
| `bool`, and its pairs (`yes/no`) | `BOOLEAN`, written `true` and `false` |
| `date` | `DATE` |
| `time` | `TIME` |
| `datetime` | `TIMESTAMP` in UTC, `TIMESTAMP_NS` when a value holds nanoseconds, written `2026-08-14T10:00:00.5Z` |
| a choice | `ENUM` of its words in their order, so `ORDER BY` sorts as the type is written |
| a reference | its key's type: `VARCHAR` for a text key, `BIGINT`, `DECIMAL` or `DATE` read from its text for those |

The width is 38 because the engine's decimals are `Decimal128(38, s)`: exact, never a `DOUBLE`. DuckDB keeps them exact through `+`, `-`, `*` and `SUM` (`0.10 + 0.20` is `0.30`, `amount * amount` a `DECIMAL(38, 4)`), but its `/` and `AVG` on decimals give a `DOUBLE`, where a formula's `/` is exact decimal to 15 significant digits: that is DuckDB's SQL, left as it is. The same column in two files must hold the same kind of value: two currencies, `num` beside `pct`, two choices of other words, or a reference to keys of two types stop the query with both files named (`money.cost: EUR in a/money.cells and USD in b/money.cells`), never coerced; a scale or a nanosecond unit differing between files is the wider. A choice can be an `ENUM` because a table of one name holds the same words in every file. A computed cell is the value its formula gives, as `cells show` writes it; a broken cell is null. When any file read has problems the answer is still written, stderr says how many (`cells sql: 3 problems in 2 files read, a broken cell read as null: cells check books`), and it exits 1; 2 is a query that cannot run (a path, a clash, an error of DuckDB's).

The columns reach DuckDB through a table function, `cells_scan`, which writes the engine's buffers into DuckDB's vectors a chunk of 2048 rows at a time: the values DuckDB holds as the engine does copied (`i64`, `i32` days, `i128` decimals raised to the column's scale, a choice's index as the `ENUM`'s), text copied into DuckDB's strings, only the columns the query reads (projection pushdown), each view (`CREATE VIEW money AS SELECT * FROM cells_scan(k)`) read as many times as the query reads it. The engine's Arrow export (`cells::arrow`) is not the path: the C API's Arrow scan, `duckdb_arrow_array_scan`, wraps one array in a stream that hands it out once (its `GetNext` sets `done`), so a table read twice, a self-join or a subquery, reads empty the second time, and the only safe use is copying the whole file into a DuckDB table; DuckDB's own zero-copy scan, `arrow_scan` with a stream factory, takes C++ function pointers the C API does not offer. A scan runs on one thread, so rows come in the files' order as `show` writes them; the parallel scan the C API allows gives up that order.

1M rows of the budget (55.8 MB, `cells-bench gen`), the whole command, best of seven, other work running (load 4 to 12):

| | ms |
|---|---|
| a one-row file, `SELECT 1` (start, DuckDB opened, the function registered) | 18.8 |
| the 1M-row file, `SELECT 1` (its read on 18 threads added) | 44.1 |
| `SELECT category, SUM(cost) FROM budget GROUP BY category` | 54.4 |
| `SELECT SUM(cost * qty) FROM budget WHERE paid AND "on" >= DATE '2025-01-01'` | 53.4 |
| `SELECT COUNT(*) FROM budget` (DuckDB asks for the first column, 1M texts copied) | 62.6 |
| `SELECT COUNT(DISTINCT item) FROM budget` | 205.8 |
| `SELECT COUNT(*) FROM budget a JOIN budget b ON a.item = b.item` | 164.6 |
| `SELECT * FROM budget`, every row written | 387.6 (`cells show`: 515.6) |

DuckDB is `cells-sql`'s alone because it costs the binary and the build: in `cells` it made it 68.1 MB built and 48.0 MB stripped, and `cells lsp`, which every editor window starts, is that binary. Apart, `cells` is 4.7 MB built and 3.6 MB stripped, `cells-sql` 62.8 MB, and a clean build of `cells-sql` takes about 2 min 17 s on 18 cores (nearly all compiling DuckDB's C++). What both read from the disk, imports followed and a folder's files, is `cells-disk`, one crate. The options weighed against this: DuckDB loaded at run time from a system install, small but tied to a version nobody pins; DuckDB trimmed, perhaps 25 to 30 MB, still too much for the language server; SQL of our own over the engine's columns, small but a language to keep up with forever (DataFusion, the Rust alternative, is as large as DuckDB). Next, the daemon links `cells-sql`'s part, so queries run over the columns it holds (ENGINE.md).

**SQL/PGQ is not in it.** `GRAPH_TABLE … MATCH` is DuckDB's community extension `duckpgq` (cwida/duckpgq-extension, MIT; the community index pins commit `9c11bc19` for DuckDB 2.0, which needs `SET active_grammar_extensions = ['duckpgq']` after loading it). The one stock way to have it is `INSTALL duckpgq FROM community`, a download from community-extensions.duckdb.org at run time, which `cells sql` never does. Built in, it would take: DuckDB 2.0.0 built with CMake and an extension config loading `duckpgq` statically at its pinned commit (`duckdb_extension_load(duckpgq GIT_URL https://github.com/cwida/duckpgq-extension GIT_TAG 9c11bc19…)`), a fetch at build time only; `libduckdb-sys` linking that build (`DUCKDB_LIB_DIR`, its static libraries and the generated extension loader) in place of `bundled`, which compiles DuckDB's amalgamation alone, and whose `bundled-cmake` refuses `DUCKDB_EXTENSION_CONFIGS` ("additional static extension libraries are not auto-linked"); a `build.rs` in `cells-sql` linking `libduckpgq_extension.a`; and the binary's size and build time measured again. Shipping the extension's own `.duckdb_extension` inside `cells-sql` and loading it from a file is not tried: a C++ extension takes DuckDB's symbols from the process, and a statically linked binary does not export them. With it, the references are the edges: a property graph named after the folder (`books`), every table a vertex table, and a table holding references also an edge table for each reference column, its source its own key, its destination the key it names (`money` needs its `id!`), labelled by the column (`MATCH (m:money)-[:account_to]->(a:accounts)`).

## WebAssembly

`bun cells-wasm/build.ts` builds it (opt-level `z`, LTO, SIMD on, `wasm-opt -Oz` when installed) and embeds it in `js/wasm.ts` as base64, so `read(text)` compiles the module synchronously, no `await init()`. 482.8 KB raw, 210.9 KB gzip, **170.2 KB brotli**, no imports (completion and hover brought 13 KB of it, looks 16 KB). Nothing in the core parses a float: a scale's point is found in exact decimal, since `str::parse::<f64>` links the float parser and its table of powers of five, 13 KB brotli. `doc.looks(locale)` gives each row's tint and, for each column with a look or a tinted choice, each cell as drawn and its tint; `column.tints` and `column.looks` say what its type and its looks give it. `read(text, { at, files })` follows the file's imports through the files a page holds, by path; `readAs(text, dialect)` reads a plain file (`detect` finds its separator), `reshape` and `writtenAs` are the columns reshaped and another dialect; `column.formula`, `column.origin(row)` and `column.targets` say what computes and what a reference names. A host that keeps its own rows (ui's table) takes every cell's text in one call (`doc.cells()`, one decode cut at offsets, never a call per cell), each header cell's type as spelled (`column.spelled`), the text before the header (`doc.prelude`), and writes a file back from its cells with `compose`, which never touches a doc; a problem says itself with its place (`why`) or without it, for the cell it sits on (`reason`), and where it is (`span`, in UTF-16 units), and what it weighs (`severity`, `Kind::severity`'s: `error` wrong, `warning` absent or behind); a column says what its cells may hold (`column.offers()`, `Doc::offers`), and `complete(doc, text, at)` and `hover(doc, text, at)` are the core's `cells::complete` and `cells::hover` at a string's index, what `cells lsp` completes and says, the tables named those the doc was read with; `doc.broken` is where the grammar breaks, and `doc.unread` the bytes after a record that does not read, which `compose` writes back. Chrome allows a synchronous `new WebAssembly.Module` and `new WebAssembly.Instance` on the main thread up to 8 MB since Chrome 115 (4 KB before), the limit taken from the largest function the spec allows ([Chrome 115 beta](https://developer.chrome.com/blog/chrome-115-beta/), [the intent to ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/nJw2zwaiJ2s/m/EYPgC5D3LwAJ)). `bun cells-wasm/js/conformance.ts [--lib <a vendored copy>]` runs the suite through the wrapper (cells and compose included); `js/bench.ts` races it against `ts/src/cells.ts`.

## Apple

`bash cells-ffi/build-apple.sh` builds aarch64-apple-darwin (all macOS 27 runs on), incrementally, strips debug info and local symbols, and writes `target/apple/CellsCore.xcframework`, the `binaryTarget` of the Swift package ([swift/README.md](../swift/README.md)), which links it by path from this same checkout. The static library is 23 MB built and 3.4 MB stripped (std included). Another platform is a slice added there when an app on it links the binding. The header carries `cells_origin`, `CellsBaseRef`, the `formula` and `reference` problem kinds, `CellsPartFormula`, `cells_read_with` and `cells_read_at`, a file read with its imports followed, and the `stale` kind with `cells_fix_stale`, `cells_keep_stale` and `cells_stored_since`, a write storing what it reached; `cells_complete`, what may be written at a byte of a doc's text (`cells::complete`, the completions `cells lsp` gives and the prelude's statements, types, schedules and declarations), each read with `cells_completion` (its kind and the bytes it replaces) and `cells_completion_part` (its label, detail, insert, filter and sort; a function's detail its call and what it gives, `ROUND(x, digits)`), the tables it names the ones the doc holds; and `cells_hover`, what is said of a byte of a doc's text (`cells::hover`, the hover `cells lsp` gives, Markdown there, plain lines here: a column, a cell, a formula's name or function, a named type, a table), read with `cells_hovered` (the bytes it speaks of) and `cells_hover_text`; how a value looks: `cells_tint`, `cells_row_tint`, `cells_type_tint` (a choice's word's tint, a column's type's or a named type's), `cells_drawn` (in a locale handed as its lines, `cells::Locale::lines`) and `cells_looks_of`, with the token kind `CellsTokenTint`, the statement kind `CellsStatementLook` and the completion kind `CellsCompletionColor`, and `cells_look_count`, `cells_look_target` and `cells_look_rules`, each look statement with the rules that read; `cells_reads`, what a computed cell reads, each column and its rows; and the charts as JSON: `cells_charts` (the file's fences), `cells_chart_summary` (what one draws), `cells_inferred_chart` and `cells_inferred_summary` (the chart a file with none is drawn from), with the statement kind `CellsStatementChart`; `cells_formatted`, a doc's text in the standard layout `cells fmt` writes; and `cells_header_cell`, a typed header cell as a writer writes it (`total: EUR = cost * qty`), the one spelling Swift's `Column.header` reads.

A C header over uniffi, by measurement: the same surface through uniffi 0.32.2 links 591 KB stripped against 518 KB, pulls 59 crates where this pulls none, and moves strings and buffers by copy, while the columns must cross as the doc's own pointers.
