# The engine

> **Not yet final**, as SPEC.md. This is the engine's design: [v0](#v0-one-mac) is what is being built, each section saying what of it is built, and [Later](#later) is the direction it is built to grow into. README.md lists what exists.

The files are the truth. The engine is a typed, current view of them, and the one place a client reads and writes through. It is to a folder of `.cells` files what git's index is to a working tree, or Spotlight's to a disk: derived, rebuilt from the text, and never in the way of anyone who edits the text without it.

The engine is a library: the Rust core, behind a C header on the Apple platforms and as wasm in a page.

## v0: one Mac

### How it runs

- **The daemon.** One process per user, `cells serve`, kept running by Cells.app (`CellsEngine.app`, a launch agent nested in the app as a login item, registered, handed to a new copy and removed with the app through swift-utils' `AppInstallations`), hosts the engine for every client on the Mac: Cells.app, the language server, the command line. Each file is parsed once and its references are held as a graph; queries and charts are to be served from memory (not built).
- **Schedules kept.** It runs each file's scripts on their schedules (SPEC.md, "Running"), through Bun, and only there: a page or an app shows what the last run stored. A script runs only at a version its person allowed; one due and not allowed is said once and waits. When a script is next due is reckoned from the last run its file records (`schedule.rs`), its times of day in its zone with daylight saving, so a run missed while the Mac slept or the engine was stopped runs once, never once per miss; a failed run is a run, never retried in a loop. `when <file> changes` runs when a change to that file is heard. A run takes the time a script takes on its own thread, and lands in its file over the version the engine holds (`cells::run`), a root of history. `cells run` asks the engine for one now.
- **What it says** is `tracing` records shaped as the utils logging contract writes them: a fixed message, its fields, and spans for a serve, a change, an edit, a restore and a run. Hosted, `CellsEngine.app` writes each through swift-utils' `Log` (JSON on `engine.trace`, the unified log, traces joined by `traceparent`); `cells serve` says them on stderr as a person reads them.
- **Three parts, each owning one thing.** `cells::folder`, in the core, decides: the folder's files, the graph of what each reads through its imports, the version of each it last knew, and from a change handed in, what to read again, what to store and which files it still needs. It reaches no disk, clock or thread, so its decisions replay exactly from the changes handed in. `cells-daemon`'s `World` is the one way to the disk, the clock and change events. Its `Daemon` joins the two: what was heard is handed in, and what was decided is carried out, logged and said. Standalone, an app holds the same `Folder` in its own process; with the daemon, it asks the daemon.
- **Standalone.** A page given a `.cells` file (the wasm engine), or an app given a file without the daemon: read, render, edit, give it back. Nothing else is needed, and a file is complete on its own.

### The protocol

Intents and queries in, results and changes out. Results are to be Arrow IPC frames (typed columns, read by the client as they arrive); commands are small messages, an intent's body the same JSON as its line in the log. Clients reach the daemon over a Unix socket, reachable only by the user's processes, the client's signature checked.

What is built (`cells-daemon`'s `wire`, `server`, `client`) speaks JSON, one object per line over `Cells/engine.sock` in the user's application support folder, so a conversation reads with `nc -U`; there are no queries and no Arrow frames yet. A client never meets a half-made socket: the engine's folder is private, a lock says which process is the engine, and the socket is bound under a name of its own, made `0600`, listening, then renamed into place, so its name answers the moment it exists. A client greets with the protocol's version and its name, and a different version parts there. It asks for folders (`serve`) and hears every file whose version changed (`changed`), the engine's own writes included; it sends intents (`intent`), approvals (`allow`), what it is editing (`editing`) and runs (`run`), and reads history (`history`, `cell`, `version`, `since`, `restore`). Who connects is the kernel's word, never the caller's (`trust.rs`): its user (`getpeereid` on a Mac, `SO_PEERCRED` on Linux, where no code is signed and the engine admits the same user, its socket in `$XDG_STATE_HOME/cells`), and on a Mac its audit token, which names the exact process, so its code signature is checked, its bundle exactly what was signed. A signed engine holds a client to its own signature: the same team, as the app (`<app id>`) or its `cells` command (`<app id>.cli`), the app id read from the engine's own identifier. Any other program of the user, a script or a binary dropped in a folder, is refused and told why: the engine is what writes a person's books. An engine with no team (a development build run by hand) has none to hold a client to and admits the same user; the trace says which at start (`admits`). Cells.app keeps the engine running: `CellsEngine.app` is a Swift `main` that watches its own image (`AppInstallations`, so a replaced, moved or deleted Cells.app takes its engine with it) and calls the Rust engine, linked as a static library through one C function (`cells_engine_serve`), so Swift owns the process's life on the Mac and Rust the engine. Where Cells.app is not installed, a client that finds nothing answering starts the engine itself (`cells serve`, detached), and the hosted engine, finding that one holding the lock, waits for it rather than being restarted against it by launchd. Either way the trace is `engine.trace` beside the socket, never a folder's log.

The language server is a client: it asks for the folder the editor names and each open file's own, and diagnoses again on every change the engine tells, watching nothing itself. Each open file's own folder too, because an editor may name no folder (Helix names none where no project marker is), and an import may climb out of the one it names; the engine watches every file a served file imports, wherever it is. One watcher serves every client, never one per client. A folder is served whole, everything under it watched and read, but for the home folder and the disk's root, which are served shallow: their own files alone, never a folder under them, so a file kept in `~` is followed without the engine crawling the disk (its log is `~/.cells/log.jsonl`).

### Reading

- **Parsed once, kept on disk.** Each file's columns are cached as Arrow, memory-mapped, keyed by the file's identity (device, inode, size, modification time) and its content hash, so a restart parses nothing and the kernel decides what stays in memory. Size and time alone never decide: two writes in one tick, or a clock stepped back, leave both equal over different bytes, so the hash does.
- **Only what changed is read again.** A file that grew with its start unchanged (its prefix hash the same: a ledger appended to) has only its tail parsed; any other change reparses that one file, at memory speed.
- **Changes are heard.** FSEvents says what changed; on a local volume it is trusted, a dropped batch rescanning only the folder it names, and after a restart the daemon asks for every event since the last one it saw. On a network or external volume, where FSEvents is unreliable, the files a query touches are checked before it is answered. Events are batched and handled at the engine's own pace. Either way, the next query serves what is on disk.
- **A query sees one moment.** It runs on a snapshot: a file changed while it runs is in the next query, never half in this one.
- **Half-written is pending.** A record cut off at a file's end (a writer caught mid-write) is pending, not a problem, and read again once the file is still.
- **Queries are DuckDB's** over the cached columns, with nothing copied: SQL, and SQL/PGQ for the graph.
- **Clients subscribe.** A query a client keeps (a chart, a table) is answered again when a file it reads changes: charts and tables are live. A subscriber too slow to keep up is told it lagged and reads again, never queued without bound.

What is built: changes are heard through the system's file watcher (`notify`, FSEvents on a Mac), a batch read once the disk has been quiet for 30 ms (delayed 500 ms at most while writes keep coming), and each changed file read again whole. The cache, tail reads, snapshots, queries and subscriptions are not built.

### Writing

- **The engine keeps the approvals** (SPEC.md, Running): `allowed.jsonl` beside its socket, one line per script allowed (its file, its name, the version shown, who asked, when), the engine its one writer through `allow` and every client its reader (`cells_daemon::allowed`). `cells allow` asks in a terminal and nowhere else; the language server warns on a script not allowed and its fix allows the version shown, and allows a script whose code the person changed in that editor as they save it; Cells.app does the same for a script written in it.
- **An edit is an intent addressed by identity**: the row `k7m2q9xa`, the column `amount`, the value `1000`. Never a row's position, which a line inserted elsewhere moves.
- **Ids are the engine's.** No intent writes an `id`; a client built on the protocol cannot show or change one. Rows without one get theirs at the engine's next write (SPEC.md, "Every row has an identity").
- **Every intent is idempotent by its own id**, eight base-32 characters made by the client: applying it a second time changes nothing and answers the first result.
- **Every intent names what it was made against**: for each file it touches, the content hash it read.
- **Applying is deterministic.** Nothing an intent applies reads a clock, a random source or the environment: its new row ids and its timestamp are assigned when it is accepted and written into it, so a replay gives the same bytes.
- **Journal, then apply.** The accepted intent is appended to the log and flushed; then each file is written: the new text beside the file, flushed, swapped into place inside an `NSFileCoordinator` write (`FileManager.replaceItemAt`, which keeps the file's metadata); then a `done` entry names each resulting hash. A crash between the two replays from the log, and a replay over a file already written is a no-op. A change across many files (an account renamed in every file that references it) is one intent, the same way.
- **Never lose anyone's write.** Locks on a Mac are advisory, honoured only by programs that cooperate, so the engine detects rather than prevents. Just before the swap, the file must still be the version the intent was made against. If someone changed it, the intent is applied to what is there now when its rows and cells are untouched, and otherwise refused, the conflict shown to the person, never resolved by guessing.
- **A change stores what it reaches, in every file** (SPEC.md, Writing): the changed file and every file reading it are read again in the order their reads need, and each is written as a write after the version the engine knew leaves it, so a computed cell whose formula now gives another value is stored, and a value typed over its `=` (its formula giving what it gave) is left stale for a person. The engine's write coming back is its own version, read alone: it stores what the files reading it already read. A file is written only over the version the write was made from; one changed since is left as its writer saved it (a `moved` line), and that change is read next and stores what it reaches.
- **An edit the engine did not make is logged too.** When the engine finds a file whose hash is not the last result it logged, it records an `external` entry (the old hash, the new one, which rows changed), so the log explains every version of every file, an editor's included.
- **Typing is not an intent.** An editor's unsaved text is presence, sent to the daemon but never logged; saves and app actions are intents.
- **Rules are checked before a write**: keys, `unique` columns, every `check` (SPEC.md, Open). An intent that would break one is refused with the reason.
- **A run is an intent.** What a script returned is checked against its table's header, then written as one intent (its rows, its entry in `runs`), journalled and applied like any edit, so a crash mid-run leaves the last run's rows whole. A run that fails writes only its failure. The script's stdout and stderr, its duration and outcome go in the log with the intent.

What is built, for one file at a time (`cells::intent`, the daemon's `intent`, `ToEngine::Intent`; the Swift binding's `Cells.Daemon.apply`):
- **The ops.** Set a cell (a row by its key or id, a column by name, its text, and `was`, the text it held when the edit was made), add a row (columns by name, the rest blank, its computed cells stored), delete a row (`was`, its line as it was). A file that has given its rows no identity yet is addressed by a row's line, and the engine names that row by the id it gives it in the same write. And the file whole (`text`), an intent's one op, what a client holding a document sends: made against the version the engine holds, it is the file, with what its changes compute stored; made against an earlier one, the cells it set and the rows it added and deleted beside that version (kept whole, so the engine compares) are applied as those ops, each saying what it saw, and a change to the prelude or the header, a row moved, or a file whose rows have no key or id is refused. The log keeps it by the version of its text (`"op":"text","version":…`), never the text twice.
- **Ids.** A Cells file with neither a key nor an `id` column gets `id: id!` at the first intent that writes it, an id in every row, and the later copy of a repeated id a new one. Ids come from random bits the daemon hands the core (`World::bits`), and the ids given are logged with the intent. No op writes one: setting it, or naming it in a row added, is refused. A plain file (a CSV, a TSV) is never given a column: its rows are named by their lines, and a row added to one is refused.
- **Against.** An intent made against the version the engine holds applies as made. Made against an earlier one, it applies only where its ops say what they saw: a cell that holds what `was` says, a row whose line reads as it did. An op that says nothing of what it saw, or finds something else, refuses the whole intent, saying what is there now. A version on disk the engine had not heard yet is heard first (its own `external` root), then the intent applies over it.
- **Rules.** An intent that leaves an error (a key repeated, a type broken, a bound crossed, a reference to no row) in a row it touched, that was not there before, is refused whole with the problem.
- **Once.** The log is where an intent's id is kept: sent again, it is answered with the version it wrote and the ids it gave, nothing applied twice.
- **Journal, then what it reached.** The intent is a root of history (`edit`), written over the version it was applied to, then every file it reaches is stored and logged as following it. Not yet built: intents across several files, the `done` entry and replay after a crash between journal and write, and the swap inside an `NSFileCoordinator`.

### The log

`.cells/log.jsonl` in the folder, one JSON line per entry: its number (`n`), the SHA-256 of the line before (`prev`, the engine's own hash, so the core keeps no dependency; an edit or a removal breaks every later link), its time (`at`, milliseconds since the Unix epoch), its kind, the file it is about (`path`, from the folder), and the kind's fields. A log whose chain breaks is still read and continued, and the break is said. The log is one file, read whole when its folder is served. There are six kinds. Four are roots:
- `external`: a version the engine did not write, with the hash before (`null` for a new file), the hash now (`null` once removed), the client that said it held that version (`by`, else none: a program outside Cells), and the cells it changed.
- `restore`: a file returned to a version by a client.
- `run`: a script's run, with its number, its outcome, what started it (its schedule, a change to a file, a client) and the cells it changed.
- `edit`: a client's intent, with its id, who sent it, its ops, the ids it gave rows, the version it was written over and the one written, and the cells it changed.

Two follow a root (`cause`, its number):
- `store`: a write the engine made of what the root reached, naming the files of the chain it reads directly (`via`), the version it was written over and the one written, and each cell stored with its value before and after.
- `moved`: a write not made, its file changed since.

Every version a line names is kept whole in `.cells/versions/<sha256>`. A `store` is logged once its file is written, not journalled before: it follows from the versions logged before it, so a crash between the two loses only a line saying what the files already show.

### History

The log is what happened; history is a person reading it: what changed, what changed it, when, and the chain each change set off. The engine reads it for every surface (`history.rs`): a folder's or a file's chains (`history`), a cell's every value (`cell`), a version whole (`version`), a file returned to one (`restore`). `cells history` draws it in a terminal, and swift-utils' `InkHistory` in Cells.app, so every surface shows one history the same way. Cells.app sends each edit of a UTF-8 file as an intent (its text whole), logged as an `edit` by the app; a file in another encoding is saved by the app and logged as an `external` version, `by` the app.

- **An event is a change with its cause.** Each entry names who made it (a person in Cells.app, an editor through `cells lsp`, `cells` in a terminal, a script's run, the engine storing what a change reached, or an outside writer: an editor without the server, `git pull`), the files and cells it changed with their values before and after (an outside edit's cells found by comparing the version before with the one after), and the entry that caused it, when one did. An outside edit, a person's edit and a script's run are roots; what the engine stores because of them points at them.
- **A chain is a root and everything it reached**, shown as one line that says what was done, by whom, when (`q4/money.cells saved in Helix · 12:42`), with what followed folded under it as a tree (`q4/money.cells row 6, cost 180.00 → 200.00`, then `quarters.cells row 2, costs 404.90 → 424.90, net 7795.10 → 7775.10`) and a count while folded (`2 files followed`). The folder's history is its chains, newest first, filtered by file (by who and by kind: not built).
- **Why, from anywhere.** A cell asks for its history: every value it held, each beside the chain that wrote it, so a total answers "why is this 424.90" with the cost saved in Q4 at 12:42. From a cell, up to the root that caused it; from a root, down to every cell it reached.
- **A column is known by what it says** (`folder::same_columns`), since a file has no column ids. The same name is the same column. Of the columns left on each side, one whose type and formula are the same and whose cells read the same, row for row, is the same column renamed, wherever it now stands: one change (`column something renamed somethingff`), none of its cells changed, its cells' history followed back through its old name. A column renamed and retyped, or renamed in the same version as one of its own cells changed, keeps only its place in common, and is one column removed and another added. Each column left before pairs with the first such column left after, in header order, so blank columns alike pair in the order they stand.
- **A version shown whole**: the file as it was after any event, its changed cells marked, beside the file now.
- **Going back is a new event.** A cell or a file returned to a version is written as a change of its own, its cause the version returned to; history is never rewritten.

### Editors

The language server is a client like any other, so an editor goes through the engine too:

- types checked as typed, references completed and followed, a rename offered across the folder;
- the id column dimmed, an id edited by hand warned about, the id column removed refused;
- ids filled in on save, through the editor's format-on-save, so a row added by hand gets its id inside the person's own save, never by a write behind them;
- unsaved edits sent to the daemon as they are typed, so another client shows the file as being edited, and a conflict shows before either side saves.

An editor cannot hide part of a line, so in one the ids are visible, dimmed and guarded; in every app built on the engine they are never shown.

What is built: `cells lsp` sends each open file's text as it is typed (`editing`), so a save lands in the log as the editor's. The id column's guards, ids filled in on save, and showing another client that a file is being edited are not built.

### Proving it

Deterministic simulation testing, as TigerBeetle's VOPR does: the real engine against a simulated world, every run from one seed, so any failure replays exactly from the seed and the commit.

- **One way to the world.** The engine reaches the filesystem, the clock, change events and coordination through one trait; production and simulation differ in that one implementation. In the core, real clocks, threads, the real filesystem and `HashMap` iteration order are banned (the core is `no_std`, its optional `std` feature adding only threads for reading).
- **The world simulated**: the daemon and its clients, and editors that ignore coordination; durability only after a flush, renames atomic but durable only once their folder is flushed; a clock that drifts and jumps, so size and time lie; FSEvents delayed, coalesced, reordered and dropped.
- **What it injects**, each probability drawn from the seed: a crash at any call into the world, torn writes, lost unflushed writes, a full disk and I/O errors, bit rot in the cache, an editor truncating, appending, inserting, reordering, reformatting, pasting a row twice or deleting the id column, two writers at once.
- **One seed, many streams**: the seed draws the world's shape and one sub-seed per subsystem, so how often one subsystem draws never shifts another's.
- **What it checks**, beside assertions on every assumption: no acknowledged write lost (it is in the files or was refused with the reason given); never half a file read; the cache equal to a fresh parse before every query; untouched rows keeping their bytes; a log replayed any number of times giving the same files; the books' rules holding in every version written.
- **Exhaustive where it is small**: every crash point of one write.

Assertions stay on in release builds, as TigerStyle says: a confused engine stops rather than writing books wrong.

What is built: the daemon's tests run it against a simulated world (files in memory, change events handed in by the test, a clock that moves only when asked, counted random bits), so every run is the same run. Seeds, fault injection and the checks above are not built.

## Later

The direction v0 is built so it never needs a rewrite to reach. None of it is being built now.

### Other devices

- **Every device a full replica.** The files sync as files (iCloud Drive, git, Syncthing); each device's engine keeps its own cache from its own files; reads, queries and records work with every other device off. On iOS the app hosts the engine itself (no daemon exists there), watching its folder through `NSFilePresenter`, asking iCloud Drive to download what it opens.
- **Books owned.** A folder names one device whose engine applies intents to it. Another device records an intent, shows it at once marked pending, and sends it to the owner, which applies it when it is in reach after checking every rule, or refuses it with the reason. The reason is money: an invoice once, a balance that must hold, a limit, a pending payment settled once are rules over many rows, and no merge of cells keeps them (two devices each recording a valid 50 from an available 80 merge into an overdraft with no cell in conflict). This is Turso's embedded replicas, the replica writing ahead of its primary as pending.
- **The transport** between devices: a mesh where devices dial keys, not addresses, end to end encrypted, paired once, with an outbox holding intents for a device out of reach.
- **The merge**, for what the engine did not write (two hand edits on two devices, a git merge, a conflict version iCloud Drive or Syncthing kept): three ways by row identity, cells compared by typed value, deletions against edits and additions on both sides as conflicts, row order never one, the result checked against the books' rules. Conflicts are a table beside the file (`.cells/conflicts/<file>.cells`), never markers in it, so the file always reads; never resolved by guessing. No file sync hands over a common ancestor (only git does), so each device keeps a store of file versions by hash and finds the ancestor through the logs. git calls the engine as its merge driver. This is Dolt's merge of tables by primary key.
- **The log per device**: one chain per device per folder, signed by the device's key and anchored in its keychain, so a chain deleted or replaced is found, and a merge's parents are known.
- **Pages connected**: a page reaching the engine over a WebSocket, paired once, its origin checked, since every page the browser visits can reach `localhost`.
- **Replicated**: devices agreeing on the order of the intent log (Viewstamped Replication, as TigerBeetle does), for books shared by several people where two writers must never both succeed. It needs an always-on replica: with two devices, consensus needs both awake for every write.

Prior art for the whole shape: Ink & Switch's [Local-first software](https://www.inkandswitch.com/local-first/) (the data on the person's devices, the network optional), Turso's replicas, Dolt, and CRDT libraries such as Automerge, which merge without asking but cannot say that two edits to an amount are a conflict, so the engine does not take them for money.
